Cypress detects flaky tests but gives teams no way to manage them over time. Before building that, measure how often it hurts, and start by alerting when a flaky test's behavior changes.

The answer up front. The rest is how I got there, what I'd confirm first, and where I could be wrong.

Core problem: flaky tests are marked flaky forever

Cypress flags flake within a run, but there's no way to triage it, contain it, fix it, or notice when it changes. The label turns into noise, until it hides a real regression.

Real bugs slip through

A test previously flagged flaky failed, the PR merged, and it was a real regression in production. Feedback D

Noise nobody can act on

Teams want to mute known flake they can't fix yet, like a third-party login page. Feedback E

Manual workarounds

Tag-and-exclude pipelines, asks for triage, and reruns just to find out what's real. Feedback A, B, C

Why this problem first, and what I set aside

Why it matters most

It has already caused production harm (D).

It runs through four of the six signals.

Cypress's design contributes: flaky tests don't affect a run's pass or fail status, and there's no alert when a flaky test's behavior changes. Input 2

Second issue: test segmentation (A, F)

Teams can't choose which tests run where: rerun only failures, run subsets, or configure shards differently. A distinct problem from flake reliability.

F is the only feedback that explicitly mentions leaving, and it may come from a larger, more sophisticated customer. Assumption

Parked, not dismissed. The prevalence check should weigh it by revenue.

Before building anything, find out how often this actually hurts

  1. How prevalent is it?

    Share of customers, projects, and runs with flaky tests, and how much of the quarter's tickets and cancellations trace back to it. Six quotes can't size this.

  2. How often does a flaky test let a real bug reach production?

    D is one incident. Cypress can't see production directly, so we'd need a proxy, like known-flaky failures on commits later reverted or hotfixed, plus customer interviews.

    Assumption: a proxy exists

  3. What telemetry do we already have on flaky tests?

    What's captured per attempt, how long it's kept, and whether it's enough to describe a test's normal flaky behavior.

First step: learn how each flaky test behaves, and alert when that changes

Capture the pattern

For each flaky test, record its normal behavior: how often it fails, on which attempts, and how it fails.

Alert on change

When that pattern changes in any way, flag it for a real look, ideally where the merge decision is made.

Assumption: a change is worth a look

Not specifying yet

What counts as a change, thresholds, where alerts appear, or a full lifecycle feature. Those depend on the three questions.

Why this first: it closes a gap Cypress already acknowledges, speaks directly to what happened in D, and produces the telemetry needed to decide whether a larger lifecycle feature is worth building.

Where I wouldn't trust my own conclusion

Where I might be wrong

I built this from six quotes Cypress selected and one production incident.

A larger lifecycle feature may be the real need, one that also covers triage, quarantine, and rerunning only failed tests (A).

I parked test segmentation (A, F) as a second issue, though it may be a big problem for a big customer.

Some product knowledge came from AI and is unverified. It's logged as assumptions.

What would change it

Flaky tests turn out to be rare, or rarely let bugs reach production.

Telemetry can't tell a changed pattern from normal flake.

Cancellations or revenue cluster around test segmentation.

Change alerts are mostly false alarms.
